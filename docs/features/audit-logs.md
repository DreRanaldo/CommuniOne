# Audit Logs and Security Auditing (Stage 11)

An append-only record of security, moderation, administrative and important
business actions. Entries are **generated by the database**, in the same
transaction as the change they describe. Applications cannot write, rewrite or
delete them.

- **Migration:** `supabase/migrations/20261011001700_audit_logs.sql`
- **Tests:**
  - `supabase/tests/database/018_audit_logs.test.sql` (pgTAP, 44)
  - `tests/integration/audit-logs.test.mjs` (end to end through the Data API)

## Audit structure

### `audit_logs`

| Column | Notes |
|---|---|
| `id` | uuid PK |
| `community_id` | The community the action belongs to. **NULL = system event** (platform level). |
| `actor_user_id` | Who did it. Always the validated session user for client actions; **NULL = system** (service role, scheduled jobs). |
| `action` | FK → `audit_actions`, e.g. `membership.suspended` |
| `entity_type`, `entity_id` | What was acted on |
| `metadata` | JSON object, ≤ 8 KiB. Identifiers, statuses and changed field *names*; **redacted** on insert. |
| `created_at` | `clock_timestamp()`, which keeps the order of several events within one transaction |

- **No foreign keys** on `community_id`, `actor_user_id` or `entity_id`, by design:
  history must survive deletion of the community, account or entity it describes.
- **No IP address or user agent.** There is no clear need yet, and they are
  personal data. If an investigation need arises, add a column fed from
  PostgREST's `request.headers` (forwarded IP), with a documented legal basis and
  a shorter retention period.

**Indexes:**

| Index | Columns |
|---|---|
| `audit_logs_community_created_idx` | `(community_id, created_at desc, id desc)` |
| `audit_logs_system_created_idx` | `(created_at desc, id desc) WHERE community_id IS NULL` |
| `audit_logs_actor_created_idx` | `(actor_user_id, created_at desc)` |
| `audit_logs_entity_idx` | `(entity_type, entity_id)` |

### `audit_actions` (catalog)

`(action, entity_type, description)`. Only actions that are actually produced
are listed. Add a new one together with its producer.

## Events recorded

| Action | Recorded when | Metadata |
|---|---|---|
| `community.created` | `create_community()` | slug, type |
| `community.updated` | community details or settings change | `changed_fields` (names only) |
| `membership.created` | a membership row is created | user_id, status |
| `membership.approved` | → active from pending, rejected or left | user_id, from, to |
| `membership.reinstated` | suspended → active | user_id, from, to |
| `membership.suspended` / `rejected` / `left` | status changes | user_id, from, to |
| `membership.removed` | membership deleted (removal, or account deletion) | user_id, previous_status |
| `role.created` / `updated` / `deleted` | custom roles (system roles are immutable) | name (and previous name) |
| `role.assigned` / `role.unassigned` | membership gains or loses a role | membership_id, user_id, role_id, role_name |
| `permission.assigned` / `permission.removed` | permission granted to or revoked from a custom role | role_id, permission key |
| `post.moderated` / `comment.moderated` | status changed by someone other than the author | author_user_id, from, to, reason (never the body) |
| `announcement.created` / `published` / `deleted` | announcement lifecycle | status, priority |
| `alert.created` / `published` / `cancelled` | alert lifecycle | severity, previous_status, reason |
| `event.created` / `event.cancelled` | event lifecycle | status, starts_at, capacity, reason |
| `document.uploaded` / `document.deleted` | upload completed / soft delete | uploaded_by, mime_type, file_size, visibility |
| `account.status_changed` | a platform admin changes an account status | from, to (system event, no community) |

**Deliberately not recorded:**

- reads;
- a user's own edits or self-deletes (e.g. an author deleting their post);
- RSVPs, reactions and comments;
- notification reads;
- the role permissions copied automatically when a community is created.

**Planned, added with their producers:**

- `invitation.created` / `invitation.revoked` (Stage 4);
- `platform_admin.granted` / `revoked`, once platform-admin management gets an API.

## Security model

| Rule | Mechanism |
|---|---|
| Database-generated | AFTER triggers on the audited tables call one service, `private.record_audit_event()` (SECURITY DEFINER, not callable by clients) |
| No impersonation | The service has **no actor parameter**. The actor is `private.actor_user_id()`: the validated session user for client requests, NULL for server code. Clients have no INSERT privilege at all. |
| System events from backend code | `public.record_system_audit_event()` (service role only) always records **actor NULL**, so it cannot attribute anything to a user |
| Append-only | No UPDATE or DELETE grants for clients **or the service role**. `audit_logs_protect_rows` and `audit_logs_protect_truncate` triggers reject UPDATE, DELETE and TRUNCATE for every role, including the table owner. |
| Retention purge | `public.purge_audit_logs(older_than)`: service role only, minimum 90 days. It is the only path that removes rows: it sets a transaction-local flag that the protection trigger honours. Clients and the service role have no DELETE privilege, so setting the flag themselves achieves nothing. |
| Read access | Community events: `has_community_permission(community_id, 'audit.view')` (Owners and Admins by default). System events: platform admins only. |
| Isolation | Administrators of one community see nothing from another. Suspended admins lose access immediately. |

```ts
// Administrators
await supabase.rpc('list_audit_logs', {
  p_community_id, p_limit: 50,                      // ≤ 200 per page, newest first
  p_cursor_created_at, p_cursor_id,                 // keyset cursor from the last row
  p_action, p_actor_user_id, p_entity_type, p_entity_id, // optional filters
});
// Platform admins: p_community_id: null → system events
```

## Privacy rules

**Never log:**

- passwords or password hashes;
- authentication, refresh or access tokens, JWTs, session ids, cookies or
  authorization headers;
- invitation secrets or one-time codes;
- API keys, private keys or other secrets;
- payment credentials (card numbers, CVV, IBAN, account numbers);
- government identifiers;
- message, post or document **contents**;
- full profile data. Use ids instead.

**Do log:**

- ids of the actor, subject and entity;
- old and new **status** values;
- the **names** of changed fields, not their values, unless the value itself is
  the audited fact (e.g. severity, a role name, a permission key);
- moderation and cancellation reasons entered by administrators.

**Enforcement, beyond producer discipline:**

- The insert trigger runs `private.redact_audit_metadata()` on every entry,
  whoever wrote it, at any nesting depth.
- Any key containing a credential marker is replaced with `"[redacted]"`:
  `password`, `secret`, `token`, `api_key`, `private_key`, `access_key`,
  `authorization`, `cookie`, `session`, `credential`, `card_number`,
  `account_number`.
- The same happens for keys that are exactly, or contain as a word, `otp`,
  `pin`, `card`, `cvv`, `cvc`, `iban`, `ssn`, `jwt` or `bearer`.
- Ordinary keys such as `shipping` or `note` are kept.
- Tests confirm that no secret value survives anywhere in the table.

**Personal data:** actor and subject ids are pseudonymous identifiers. On an
erasure request, keep the entries (security records), since the ids no longer
resolve to a profile once the account is deleted. If full anonymisation is
legally required, run a documented one-off operation as the database owner.

## Retention considerations

- **Default:** keep indefinitely until a policy is set. The purge enforces a
  minimum of 90 days.
- **Suggested:** 1–2 years for community events, longer for platform security
  events, subject to legal review.
- **Schedule:** run `select public.purge_audit_logs(interval '730 days');` from
  a service-role job (pg_cron or a scheduled Edge Function).
- **Archiving:** for long-term retention, export to cold storage before purging.
- **Tamper evidence:** the table is append-only inside the database, but a
  superuser can still alter it. For stronger guarantees, ship entries to an
  external write-once store or add a hash chain (future work).

## Known limitations

- No IP address or user-agent capture (see above).
- No hash-chain tamper evidence.
- Invitation events wait for Stage 4.
- Audit writes happen synchronously in the same transaction as the change.
  This guarantees completeness at a small write cost.
