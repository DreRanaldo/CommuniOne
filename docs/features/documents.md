# Documents and File Storage (Stage 10)

Secure community document management. **Files live in Supabase Storage**, in the
private bucket `documents`. PostgreSQL stores only metadata. Two independent
layers enforce access:

1. RLS on the metadata tables (`documents`, `document_folders`);
2. RLS policies on `storage.objects`, which govern the files themselves.

The storage policies do not assume the metadata RLS protects anything. They
re-check the rules through SECURITY DEFINER helpers.

- **Migration:** `supabase/migrations/20261011001600_documents.sql`
- **Tests:**

## Database structure

### `documents`

| Column | Notes |
|---|---|
| `community_id` | NOT NULL, FK **RESTRICT**, immutable |
| `uploaded_by` | NOT NULL. Always the validated session user, immutable. FK **RESTRICT** (same accountability decision as alerts and events). |
| `folder_id` | Optional. FK `(folder_id, community_id)` → `document_folders(id, community_id)`, so the folder must be in the **same community**. **SET NULL** if the folder is deleted. |
| `name` | **Display name only,** sanitised (see "File security"), ≤ 255 chars. Never part of the storage path. |
| `mime_type` | FK → `document_mime_types` (allow-list) |
| `file_extension` | From the allow-list, **not from the file name** |
| `storage_path` | **Generated:** `communities/{community_id}/documents/{id}/file.{ext}`. Unique, and cannot be chosen or changed. |
| `file_size` | Bytes. Final value is what Storage recorded. |
| `visibility` | `members` (anyone with `documents.view`) \| `managers` (only `documents.manage`) |
| `status` | `pending_upload` \| `active` \| `archived` \| `deleted` |
| `uploaded_at`, `archived_at`, `deleted_at`, `file_purged_at`, `updated_by_user_id` | Server-stamped |
| `created_at`, `updated_at` | |

### `document_folders` (optional organisation)

| Column | Notes |
|---|---|
| `community_id` | Community scope |
| `parent_folder_id` | FK `(parent_folder_id, community_id)`: the same community only. **SET NULL** on parent deletion, so subfolders move to the top level. |
| `name` | 1–120 chars; no `/`, `\` or control characters; unique per parent (case-insensitive) |
| `created_by` | Session default |

- Moving a folder inside itself (a cycle) is rejected.
- Folders are visible with `documents.view` and managed with `documents.manage`.

### Configuration

| Table | Contents | Writable by |
|---|---|---|
| `document_upload_settings` | single row: `max_file_size_bytes` (default **25 MiB**, at most the 50 MiB bucket ceiling) | service role / SQL |
| `document_mime_types` | `(mime_type, extension, enabled)` | service role / SQL |

Clients can read both, to validate uploads in the UI.

**Allowed types:**

| MIME type | Extension |
|---|---|
| `application/pdf` | pdf |
| `image/png` | png |
| `image/jpeg` | jpg |
| `image/webp` | webp |
| `text/plain` | txt |
| `text/csv` | csv |
| Word document (OOXML) | docx |
| Excel workbook (OOXML) | xlsx |
| PowerPoint presentation (OOXML) | pptx |

Active content (HTML, SVG, JavaScript, executables) is deliberately excluded.

### Indexes

| Index | Columns |
|---|---|
| `documents_community_created_idx` | `(community_id, status, created_at desc, id desc)` |
| `documents_folder_idx` | `(folder_id, created_at desc)` |
| `documents_storage_path_key` | unique `storage_path` |
| `documents_uploaded_by_idx` | `uploaded_by` |
| `document_folders_unique_name` | unique, per parent |

## Storage structure

```
bucket: documents   (private, file_size_limit 50 MiB, allowed_mime_types = enabled allow-list)
└── communities/
    └── {community_id}/
        └── documents/
            └── {document_id}/
                └── file.{ext}
```

- **Every path is generated by the database.** User-supplied names never touch
  Storage.
- The bucket is created by the migration, so local, staging and production are
  identical.
- Storage itself also rejects files over 50 MiB and content types outside the
  allow-list.

## Storage policies (`storage.objects`)

| Operation | Allowed when | Helper |
|---|---|---|
| SELECT (download, signed URL, list) | An exact `storage_path` match exists, and the document is `active` or `archived` and visible to the caller under the metadata rules. The uploader and managers can also read a `pending_upload` row, because Storage reads the row back after an upload. | `private.can_read_document_object` |
| INSERT (upload) | An exact match with a **`pending_upload`** document created by the caller, who still holds `documents.upload` | `private.can_upload_document_object` |
| UPDATE (upsert, move, replace) | **No policy, so always refused.** Stored files are immutable. | – |
| DELETE | Only an abandoned **`pending_upload`**, by its uploader or a manager | `private.can_delete_document_object` |

- `anon` has no policy, and the bucket is private, so there are no public URLs.
- Exact path matching means crafted paths match nothing: another community's
  prefix, `../` segments, other documents' paths, other file names.

**Why clients do not delete files of deleted documents:**

- Storage deletes run as `DELETE … WHERE name IN (…)`. Postgres only lets that
  statement delete rows the caller can read.
- Deleted documents' files are deliberately unreadable to everyone.
- Files of deleted documents are therefore removed by the **service-role purge
  job**:
  1. `rpc('list_document_files_to_purge', { p_retention })` lists deleted
     documents past retention (default 30 days) and pending uploads abandoned
     for more than a day;
  2. the job removes those files through the Storage API;
  3. it sets `file_purged_at`, or deletes the stale pending rows.
- The retention period doubles as a recovery window.

## Permissions

| Permission | Allows |
|---|---|
| `documents.view` | List and download `members`-visible active documents; see folders |
| `documents.upload` | Upload; rename, move or delete **your own** documents; discard your own pending uploads |
| `documents.manage` | Everything on any document in the community: restricted (`managers`) documents, visibility changes, archive and restore, folders |

Default roles: Owners and Admins hold all three; Moderators and Members hold
`documents.view`. Communities can grant `documents.upload` alone to a custom
"Uploader" role. Nothing checks a role name.

## Metadata RLS

| Status | Visible to |
|---|---|
| `active`, visibility `members` | `documents.view` or `documents.manage` |
| `active`, visibility `managers` | `documents.manage` |
| `archived` | `documents.manage` |
| `pending_upload`, `deleted` | `documents.manage`, or the uploader holding `documents.upload` |

**Writes:**

| Operation | Rule |
|---|---|
| INSERT | **No client INSERT.** Metadata is created only by `create_document_upload()` after validation. |
| UPDATE | Manager, or the uploader holding `documents.upload`. Writable columns: `name`, `folder_id`, `visibility`, `status`. |
| DELETE | Never; deletion is soft |

The `enforce_document_write` trigger additionally enforces:

- **immutable:** community, uploader, MIME type, extension, size, storage path;
- **manager only:** archive and restore, and visibility changes;
- **manager or uploader:** active or archived → deleted, and cancelling a pending upload;
- **deleted is terminal;**
- **names** are re-sanitised on every write.

## File security: nothing from the client is trusted

| Client input | Server-side handling |
|---|---|
| File name | Path components stripped (`../../etc/passwd.pdf` → `passwd.pdf`), control characters removed, trimmed, dot-only names rejected. **Display only.** |
| MIME type | Must be on the enabled allow-list. The extension comes from the allow-list (`invoice.exe` declared as PDF is stored as `file.pdf`). On completion, the type **Storage recorded** must equal it. |
| File size | Declared size must be 1 … `max_file_size_bytes`. On completion, the size **Storage recorded** is re-checked and stored, so lying about the size fails. The bucket also caps at 50 MiB. |
| Storage path | Generated column; only exact matches pass the storage policies |
| Community ID | `documents.upload` checked in that community; immutable; folders bound by composite FK |
| Uploader ID | Always the session user; not writable |

**Known limitation:** Postgres cannot inspect file bytes, so the recorded content
type is the one the client sent at upload. The allow-list excludes active types,
and the bucket enforces it too. Content sniffing or a malware scan would be a
future Edge Function step before `complete_document_upload`.

## Upload and download flow

```
client                              Postgres (RPC + RLS)                Supabase Storage
  │ create_document_upload(...) ──►  validate perm/type/size/folder
  │ ◄── {document_id, storage_path}  insert documents(pending_upload)
  │ upload(storage_path, file) ──────────────────────────────────────►  INSERT policy: matching pending doc,
  │                                                                     uploader, documents.upload
  │ complete_document_upload(id) ─►  read storage.objects metadata
  │ ◄── document (active)            (size, content type) → active
  │
  │ createSignedUrl(storage_path) ───────────────────────────────────►  SELECT policy: visible active doc
  │ ◄── short-lived signed URL ◄──────────────────────────────────────
```

```ts
const { data: [{ document_id, storage_path }] } = await supabase.rpc('create_document_upload', {
  p_community_id, p_name: file.name, p_mime_type: file.type, p_file_size: file.size,
  p_folder_id /* optional */, p_visibility: 'members' /* 'managers' needs documents.manage */,
});
await supabase.storage.from('documents').upload(storage_path, file, { contentType: file.type });
await supabase.rpc('complete_document_upload', { p_document_id: document_id });

// Download
const { data } = await supabase.storage.from('documents').createSignedUrl(doc.storage_path, 60);

// Manage
await supabase.from('documents').update({ name: 'New name.pdf' }).eq('id', id);   // rename
await supabase.from('documents').update({ folder_id }).eq('id', id);              // move
await supabase.from('documents').update({ status: 'archived' }).eq('id', id);     // managers
await supabase.from('documents').update({ status: 'deleted' }).eq('id', id);      // soft delete

// List (newest first, keyset, at most 100 per page)
await supabase.rpc('list_documents', { p_community_id, p_folder_id, p_root_only, p_statuses, p_limit,
                                       p_cursor_created_at, p_cursor_id });
```

## Verification highlights

- **Storage matches metadata:** for six users (Owner, Admin, viewer, uploader,
  another community, a pending member), the set of downloadable files equals
  the set of visible documents.
- **Through the real Storage API:**
  - uploads to another community's path, a traversal path, another file name or
    an arbitrary name all fail;
  - overwriting with `upsert` fails and the content is unchanged;
  - `text/html` is refused by both the database and the bucket;
  - a client that declares 100 bytes and uploads 3,000 is refused at completion;
  - signed URLs are denied for restricted, archived, deleted and cross-community
    files;
  - the private bucket has no working public URL;
  - unauthorized deletes, and deletes of an active document's file even by a
    manager, remove nothing.

## Known limitations

- **No byte-level type detection or malware scanning** (see above).
- **No per-community storage quota.**
- **No versioning.** A new version is a new document.
- **The purge job must be scheduled by operations,** for example with an Edge
  Function on a cron. Until it runs, deleted files remain in Storage, but
  unreadable.
- **Account deletion is blocked for uploaders.** `uploaded_by` is
  `ON DELETE RESTRICT`, which is the same open accountability decision as alerts
  and events.
